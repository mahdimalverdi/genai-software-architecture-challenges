## مسئله‌ی اصلی
این مقاله توضیح می‌دهد که سامانه‌های یادگیری ماشین نسبت به نرم‌افزارهای سنتی بدهی فنی پنهان و پیچیده‌تری تولید می‌کنند. مشکل فقط کد مدل نیست؛ داده، featureها، pipeline آموزش، وابستگی‌های پنهان، configuration، feedback loop و تغییرات محیطی می‌توانند بدهی فنی ایجاد کنند.

## پیام محوری
در سامانه‌های ML، بخش کوچکی از سیستم «کد مدل» است و بخش عمده‌ی پیچیدگی در زیرساخت، داده، glue code، pipelineها و تعامل با محیط پنهان می‌شود. بنابراین معماری باید ML را به‌عنوان یک سیستم نرم‌افزاری بلندمدت با هزینه نگه‌داری بالا ببیند، نه صرفاً یک مدل دقیق.

## ارتباط با معماری نرم‌افزار
این منبع برای گزارش نقش پایه‌ای دارد، چون نشان می‌دهد چالش‌های معماری GenAI و LLMOps ادامه‌ی یک مسئله قدیمی‌تر هستند: وقتی رفتار سیستم به داده و مدل وابسته می‌شود، بدهی فنی از کد به کل زنجیره‌ی داده-مدل-عملیات گسترش پیدا می‌کند.

|---|---|---|---|---|
| وابستگی پنهان میان داده، feature و مدل | data / training pipeline | maintainability، evolvability | تغییر کوچک در داده می‌تواند رفتار سیستم را غیرمنتظره تغییر دهد | مفهوم hidden dependencies |
| glue code و pipeline پیچیده پیرامون مدل | integration / orchestration | maintainability | سهم زیادی از سیستم صرف اتصال اجزا می‌شود | اشاره به glue code و pipeline jungle |
| configuration debt | deployment / ops | reliability، reproducibility | بازتولید رفتار مدل و rollback دشوار می‌شود | تاکید مقاله بر config به‌عنوان منبع بدهی |
| feedback loop و تغییر توزیع داده | runtime / monitoring | accuracy، stability | رفتار سیستم در زمان تغییر می‌کند | تعامل مدل با محیط و داده‌های آینده |

## معیارها و شاخص‌های ارزیابی

- معیار: نسبت کد مدل به کد glue/infrastructure
- کاربرد: تشخیص اینکه سیستم واقعاً چقدر مدل‌محور یا زیرساخت‌محور است
- محدودیت: عدد خام به‌تنهایی کیفیت معماری را نشان نمی‌دهد

- معیار: قابلیت بازتولید training و inference
- کاربرد: سنجش کنترل روی نسخه‌ها و configuration
- محدودیت: در سیستم‌های بزرگ پرهزینه است

- معیار: drift و تغییر رفتار پس از انتشار
- کاربرد: پایش بدهی ناشی از تغییر داده و محیط
- محدودیت: drift همیشه مستقیماً به افت ارزش محصول تبدیل نمی‌شود

## کیفیت و محدودیت منبع

- نوع شواهد: مقاله تحلیلی و تجربه‌محور درباره سامانه‌های ML در production
- قوت اصلی: صورت‌بندی بسیار اثرگذار بدهی فنی پنهان در ML
- ضعف اصلی: پیش از عصر LLM و GenAI نوشته شده و به مسائل خاص RAG، prompt injection یا LLM-as-a-service نمی‌پردازد
- میزان اتکا در گزارش: بسیار بالا برای چارچوب بدهی فنی و متوسط برای جزئیات خاص GenAI

- بخش تحلیل MLOps/LLMOps و ضرورت observability، versioning و governance

## جمع‌بندی نهایی برای این منبع

این منبع به گزارش کمک می‌کند نشان دهد چالش‌های معماری GenAI تصادفی یا صرفاً محصول بزرگ‌تر شدن مدل‌ها نیستند. ریشه‌ی بسیاری از این چالش‌ها در ماهیت سامانه‌های ML است: وابستگی به داده، رفتار غیرقطعی، تغییر در زمان اجرا و نیاز شدید به monitoring و governance.
