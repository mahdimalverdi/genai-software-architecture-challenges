## مسئله‌ی اصلی
این منبع مسئله‌ی ارزیابی سامانه‌های بازیابی‌افزوده (RAG) را بررسی می‌کند. در RAG کیفیت نهایی فقط به مدل مولد وابسته نیست؛ کیفیت retrieval، کیفیت context، میزان پوشش شواهد، وفاداری پاسخ به شواهد، و سودمندی پاسخ برای کاربر همگی باید جداگانه سنجیده شوند.

## پیام محوری
ارزیابی RAG باید چندسطحی و چندمعیاره باشد. ارزیابی صرف پاسخ نهایی کافی نیست، چون ممکن است پاسخ ظاهراً خوب باشد اما به سند نامعتبر تکیه کند، یا سند درست بازیابی شده باشد اما مدل پاسخ را نادرست تولید کند. بنابراین معماری evaluation باید هم اجزای pipeline و هم خروجی end-to-end را بسنجد.

## ارتباط با معماری نرم‌افزار
این منبع برای گزارش معماری اهمیت دارد چون evaluation را به یک concern معماری تبدیل می‌کند. در سرویس RAG، ارزیابی باید در CI، آزمایش نسخه‌های retriever، پایش production، regression testing و تصمیم‌های release حضور داشته باشد.

## معیارها و شاخص‌های ارزیابی

- معیار: retrieval precision / recall
- کاربرد: سنجش کیفیت بازیابی شواهد
- محدودیت: کیفیت پاسخ نهایی را به‌تنهایی نشان نمی‌دهد

- معیار: faithfulness / groundedness
- کاربرد: سنجش وابستگی پاسخ به context
- محدودیت: داوری آن در پاسخ‌های پیچیده دشوار است

- معیار: answer relevance / correctness
- کاربرد: سنجش ارتباط و درستی پاسخ نسبت به سؤال
- محدودیت: به ground truth یا evaluator معتبر نیاز دارد

- معیار: end-to-end task success
- کاربرد: سنجش اثر واقعی RAG بر کاربر یا وظیفه‌ی محصول
- محدودیت: به سناریوی کاربردی وابسته است و تعمیم‌پذیری محدود دارد

## کیفیت و محدودیت منبع

- نوع شواهد: مرور و طبقه‌بندی معیارها، benchmarkها و روش‌های ارزیابی RAG
- قوت اصلی: فراهم‌کردن نقشه‌ی جامع برای طراحی evaluation pipeline
- ضعف اصلی: بسیاری از معیارهای ارزیابی هنوز به کیفیت داده‌ی مرجع یا داور LLM وابسته‌اند
- میزان اتکا در گزارش: بالا برای بخش ارزیابی، monitoring و regression testing در RAG

## جایگاه در گزارش نهایی

- بخش ارزیابی سامانه‌های RAG
- بخش معیارهای کیفیت و reliability
- بخش observability و decision gate برای release

## نکته‌های قابل نقل یا استفاده

- ارزیابی RAG باید هم retrieval و هم generation را پوشش دهد.
- بدون evaluation set پایدار، اصلاح prompt یا retriever ممکن است باعث regression پنهان شود.
- معیارهای خودکار مفیدند، اما برای تصمیم‌های حساس باید با داوری انسانی یا benchmark معتبر تکمیل شوند.

## جمع‌بندی نهایی برای این منبع

این منبع مکمل عملیاتی منابعی مثل RAGAS و failure points است. اگر آن منابع نشان می‌دهند RAG کجا خراب می‌شود و چگونه می‌توان آن را اندازه‌گیری کرد، این survey نقشه‌ی گسترده‌تری از معیارها و روش‌های ارزیابی فراهم می‌کند. در گزارش نهایی، از این منبع برای دفاع از ضرورت evaluation pipeline مستقل و چندلایه استفاده می‌شود.
