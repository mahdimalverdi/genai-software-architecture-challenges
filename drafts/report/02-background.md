# ۲. پیش‌زمینه و مفاهیم کلیدی

## ۲.۱ مدل زبانی بزرگ در سامانه‌ی نرم‌افزاری

مدل زبانی بزرگ، در ساده‌ترین بیان، مؤلفه‌ای است که بر اساس ورودی متنی و context، خروجی متنی تولید می‌کند. اما در سطح سامانه، مدل فقط یک تابع ساده نیست. رفتار آن به prompt، ترتیب اطلاعات، محدودیت context window، نسخه‌ی مدل، temperature، سیاست‌های decoding و حتی قالب خروجی وابسته است. بنابراین در طراحی معماری، مدل باید به‌عنوان یک مؤلفه‌ی probabilistic و versioned دیده شود، نه یک کتابخانه‌ی deterministic.

این نگاه چند پیامد دارد. اول اینکه خروجی مدل باید قابل ارزیابی و پایش باشد. دوم اینکه تغییر مدل یا prompt باید مانند تغییر کد یا تغییر schema مدیریت شود. سوم اینکه باید برای شکست مدل، پاسخ ضعیف، hallucination یا latency بالا، سیاست fallback و degradation وجود داشته باشد. چهارم اینکه اگر مدل به ابزارها وصل می‌شود، نباید اختیار اجرای action بدون کنترل معماری داشته باشد.

منبع `vaswani2017attention` در این گزارش بیشتر از منظر مبنایی استفاده می‌شود؛ یعنی توضیح اینکه مدل‌های Transformer و attention چگونه زمینه‌ی ظهور LLMهای امروزی را فراهم کردند. اما تمرکز گزارش، تحلیل داخلی Transformer نیست، بلکه اثر معماری استفاده از چنین مدل‌هایی در سامانه‌های نرم‌افزاری است.

## ۲.۲ RAG چیست و چرا وارد معماری می‌شود؟

بازیابی‌افزوده یا Retrieval-Augmented Generation با این ایده شکل می‌گیرد که مدل به‌جای اتکا به دانش ثابت درون وزن‌های خود، هنگام پاسخ‌گویی از منابع بیرونی هم استفاده کند. در یک pipeline رایج RAG، اسناد ابتدا ingest و chunk می‌شوند، سپس embedding تولید می‌شود و در vector store قرار می‌گیرد. هنگام درخواست کاربر، query به فضای embedding برده می‌شود، اسناد مرتبط بازیابی می‌شوند، گاهی reranking انجام می‌شود، context به prompt اضافه می‌شود و مدل پاسخ نهایی را تولید می‌کند.

این معماری در ظاهر ساده است، اما از نظر معماری چند نکته‌ی مهم دارد. RAG یک مؤلفه نیست؛ یک زنجیره است. هر مرحله‌ی این زنجیره می‌تواند خطا ایجاد کند. اگر chunking بد باشد، اسناد ناقص وارد index می‌شوند. اگر embedding مناسب نباشد، retrieval ضعیف می‌شود. اگر top-k بد تنظیم شود، context ناکافی یا شلوغ می‌شود. اگر prompt assembly درست نباشد، مدل از context استفاده نمی‌کند. اگر evaluator وجود نداشته باشد، پاسخ غلط تشخیص داده نمی‌شود.

منابعی مانند `lewis2020rag`، `gao2023ragSurvey`، `gupta2024ragComprehensiveSurvey` و `zhao2024ragAigcSurvey` از این جهت در گزارش مهم‌اند که نشان می‌دهند RAG فقط یک تکنیک افزایش دانش نیست، بلکه یک الگوی معماری برای اتصال مدل به دانش بیرونی است. همین اتصال، هم فرصت ایجاد می‌کند و هم ریسک: فرصت برای به‌روزرسانی دانش و کاهش hallucination؛ ریسک برای خطای بازیابی، آلودگی منبع، prompt injection غیرمستقیم و دشواری observability.

## ۲.۳ ارزیابی در GenAI چرا متفاوت است؟

در نرم‌افزارهای کلاسیک، تست‌ها معمولاً انتظار خروجی مشخصی دارند. اما در سامانه‌های GenAI، خروجی ممکن است از نظر لفظی متفاوت ولی از نظر معنایی درست باشد. همچنین ممکن است خروجی روان و قانع‌کننده باشد، اما پشتوانه‌ی واقعی نداشته باشد. بنابراین ارزیابی باید فراتر از مقایسه‌ی رشته‌ای خروجی باشد.

در RAG، معیارهایی مانند relevance، faithfulness، context precision و context recall اهمیت پیدا می‌کنند. در سامانه‌های عمومی‌تر، معیارهایی مانند correctness، completeness، harmfulness، groundedness و consistency مطرح می‌شوند. منابعی مانند `es2023ragas`، `liu2023geval`، `zheng2023llmJudge`، `yu2024ragEvaluationSurvey` و `saadfalcon2023ares` نشان می‌دهند که evaluation pipeline خود باید به‌عنوان بخشی از معماری طراحی شود.

این موضوع در گزارش بعداً به یک اصل معماری تبدیل می‌شود: evaluation نباید فعالیتی دستی و پسینی باشد؛ باید در چرخه‌ی توسعه و عملیات سیستم قرار بگیرد. به بیان دیگر، همان‌طور که CI/CD برای کد اهمیت دارد، quality gates و regression evaluation برای مدل، prompt، index و corpus هم اهمیت دارند.

## ۲.۴ serving و هزینه‌ی عملیاتی

مدل‌های زبانی بزرگ از نظر اجرا پرهزینه‌اند. latency، throughput، مصرف حافظه، batching، KV cache، prefill و decode همگی بر تجربه‌ی کاربر و هزینه‌ی سیستم اثر دارند. منابعی مانند `kwon2023pagedattention`، `zheng2023sglang`، `zhong2024distserve` و `li2024llmInferenceServingSurvey` نشان می‌دهند که serving LLMها یک مسئله‌ی جدی معماری و زیرساختی است.

از دید معماری نرم‌افزار، پرسش فقط این نیست که کدام مدل دقیق‌تر است. باید پرسید آیا برای همه‌ی درخواست‌ها باید مدل بزرگ استفاده شود؟ آیا می‌توان model routing داشت؟ آیا caching پاسخ یا context ممکن است؟ آیا سیستم fallback دارد؟ آیا برای latency بالا سیاست timeout و degradation تعریف شده؟ آیا ظرفیت GPU و memory با الگوی ترافیک سازگار است؟ این پرسش‌ها نشان می‌دهند که GenAI در production بدون طراحی serving و capacity planning، ناپایدار و گران می‌شود.

## ۲.۵ LLMOps، RAGOps و governance

در سامانه‌های GenAI، چرخه‌ی عمر فقط شامل کد نیست. مدل، prompt، داده، embedding model، index، evaluator و policyها هم نسخه دارند و تغییر می‌کنند. بنابراین عملیات چنین سامانه‌هایی به رویکردی شبیه MLOps ولی گسترش‌یافته نیاز دارد. منابعی مانند `stone2025navigatingMlops`، `huyen2025aiEngineering`، `engineeringAiSystems2025` و `xu2025ragops` این موضوع را از زاویه‌ی lifecycle، monitoring و governance برجسته می‌کنند.

اگر تیم نداند کدام نسخه‌ی prompt با کدام نسخه‌ی index و کدام نسخه‌ی مدل در production بوده، عیب‌یابی و rollback دشوار می‌شود. اگر quality owner مشخص نباشد، کیفیت خروجی بین تیم‌های محصول، داده، backend، مدل و عملیات پخش می‌شود. اگر logها شامل داده‌ی حساس باشند، مسئله‌ی privacy ایجاد می‌شود. اگر risk register و policy وجود نداشته باشد، سیستم ممکن است در برابر ریسک‌های امنیتی و اخلاقی آسیب‌پذیر شود.

به همین دلیل، governance در این گزارش یک بحث حاشیه‌ای نیست؛ بخشی از معماری عملیاتی سامانه است.
