# ۱. مقدمه و صورت مسئله

## ۱.۱ مسئله از کجا شروع می‌شود؟

رشد مدل‌های زبانی بزرگ باعث شده است که بسیاری از سامانه‌های نرم‌افزاری بتوانند قابلیت‌هایی مانند پاسخ‌گویی طبیعی، خلاصه‌سازی، جست‌وجوی معنایی، تولید متن، تحلیل سند، تولید کد و تصمیم‌یار هوشمند را در خود جای دهند. در نگاه اول، ممکن است اضافه کردن GenAI به یک محصول شبیه فراخوانی یک API مدل به نظر برسد: ورودی به مدل داده می‌شود و خروجی دریافت می‌شود. اما تجربه‌ی عملی و منابع بررسی‌شده نشان می‌دهند که این تصویر بسیار ساده‌سازی‌شده است.

در یک محصول واقعی، مدل معمولاً به‌تنهایی کار نمی‌کند. قبل از فراخوانی مدل، داده جمع‌آوری، پاک‌سازی، chunk، embedding و index می‌شود. هنگام درخواست کاربر، query ممکن است بازنویسی شود، چند سند بازیابی شود، context ساخته شود، prompt نهایی شکل بگیرد، مدل پاسخ دهد، پاسخ ارزیابی یا فیلتر شود و سپس خروجی به کاربر یا یک سیستم دیگر تحویل داده شود. اگر سیستم ابزارمحور باشد، مدل ممکن است تصمیم بگیرد API یا action مشخصی را اجرا کند. در چنین شرایطی، خطا فقط از مدل نمی‌آید؛ خطا می‌تواند از داده، بازیابی، رتبه‌بندی، prompt، سیاست‌های امنیتی، ابزارها، evaluator یا pipeline عملیاتی ناشی شود.

به همین دلیل، پرسش اصلی این گزارش چنین است:

> در طراحی سامانه‌های نرم‌افزاری مبتنی بر GenAI، به‌ویژه سامانه‌های RAG و ابزارمحور، چه چالش‌های معماری تکرارشونده‌ای پدیدار می‌شود و چه تاکتیک‌هایی می‌تواند این چالش‌ها را کنترل کند؟

## ۱.۲ چرا این موضوع معماری نرم‌افزار است؟

مسئله‌ی اصلی این نیست که مدل چه معماری داخلی دارد یا attention چگونه کار می‌کند؛ هرچند دانستن این مفاهیم برای فهم محدودیت‌ها مفید است. مسئله‌ی اصلی در سطح معماری نرم‌افزار این است که چگونه باید یک سیستم قابل اتکا، قابل پایش، قابل نگه‌داری و امن بر پایه‌ی مدلی ساخت که خروجی آن قطعی نیست و رفتار آن با prompt، context و نسخه‌ی مدل تغییر می‌کند.

در سامانه‌های کلاسیک، بسیاری از ویژگی‌های کیفی با الگوها و تاکتیک‌های شناخته‌شده مدیریت می‌شوند؛ برای مثال، availability با replication و failover، performance با caching و scaling، امنیت با authorization و input validation، و maintainability با modularity و testing. در سامانه‌های GenAI، این تاکتیک‌ها هنوز مهم‌اند، اما کافی نیستند. چون اجزای جدیدی وارد معماری می‌شوند که رفتار آن‌ها کمتر قابل پیش‌بینی است: مدل زبانی، prompt، embedding model، vector store، retriever، evaluator، agent و tool invocation.

برای نمونه، اگر یک پاسخ اشتباه تولید شود، تیم باید بتواند بفهمد مشکل از کجاست: آیا query کاربر بد فهمیده شده؟ آیا اسناد اشتباه بازیابی شده‌اند؟ آیا context کافی نبوده؟ آیا prompt نهایی ابهام داشته؟ آیا مدل hallucination کرده؟ آیا evaluator خطا را تشخیص نداده؟ یا آیا corpus قدیمی شده است؟ پاسخ به این پرسش‌ها بدون طراحی مشاهده‌پذیری، logging و trace در سطح معماری ممکن نیست.

همین مسئله در امنیت هم دیده می‌شود. در سامانه‌های GenAI، ورودی کاربر یا محتوای بازیابی‌شده فقط داده نیست؛ ممکن است حاوی دستور باشد. این موضوع مرز سنتی میان data و instruction را مبهم می‌کند. بنابراین کنترل امنیتی فقط در سطح API gateway یا احراز هویت کافی نیست؛ باید در سطح prompt، context، retrieval source، tool permission و policy gate هم طراحی شود.

## ۱.۳ تفاوت demo با سیستم production

بسیاری از سامانه‌های GenAI در مرحله‌ی نمونه‌سازی سریع موفق به نظر می‌رسند. یک prompt خوب، چند سند نمونه و یک مدل قدرتمند می‌تواند خروجی قانع‌کننده تولید کند. اما فاصله‌ی demo تا production معمولاً در همین چالش‌های معماری آشکار می‌شود.

در محیط واقعی، corpus تغییر می‌کند، کاربران ورودی‌های متنوع و گاهی خصمانه می‌دهند، مدل‌ها نسخه عوض می‌کنند، latency و هزینه اهمیت پیدا می‌کند، تیم محصول نیاز به metric دارد، تیم امنیت نگران data leakage است، تیم عملیات به monitoring و rollback نیاز دارد، و مدیران محصول می‌خواهند بدانند چه کسی مالک کیفیت خروجی است. این‌ها مسئله‌هایی نیستند که صرفاً با انتخاب مدل قوی‌تر حل شوند.

از این زاویه، معماری سامانه‌های GenAI باید چند دغدغه را همزمان پاسخ دهد:

- کیفیت پاسخ و groundedness؛
- امنیت prompt، retrieval و tool invocation؛
- مشاهده‌پذیری خطا در زنجیره‌ی چندمرحله‌ای؛
- ارزیابی پیوسته و regression testing؛
- هزینه و latency در serving؛
- lifecycle management برای مدل، prompt، index و داده؛
- governance و مالکیت کیفیت.

این گزارش، این دغدغه‌ها را به‌عنوان چالش‌های معماری بررسی می‌کند و تلاش می‌کند از منابع مختلف، یک تصویر منسجم برای طراحی سامانه‌های GenAI در production بسازد.
