# برنامه‌ی ترکیب و تحلیل منابع

این سند مشخص می‌کند بعد از خلاصه‌کردن منابع، چطور از خلاصه‌ها به گزارش تحلیلی برسیم.

## اصل اصلی

گزارش نهایی نباید فهرست خلاصه‌ی مقاله‌ها باشد. منابع باید بر اساس محورهای معماری ترکیب شوند. یعنی به جای اینکه بگوییم «مقاله‌ی اول چه گفت، مقاله‌ی دوم چه گفت»، باید بگوییم «در چالش امنیت، منابع مختلف چه می‌گویند و چه تصویری از مسئله می‌سازند».

## محورهای ترکیب

### ۱. داده، زمینه و کیفیت ورودی

پرسش‌های راهنما:

- کیفیت خروجی چقدر به کیفیت داده و زمینه وابسته است؟
- کدام تصمیم‌های معماری برای کنترل داده، زمینه و حافظه لازم است؟
- چه ریسک‌هایی از داده‌ی ناقص، قدیمی، آلوده یا نامرتبط ایجاد می‌شود؟

### ۲. بازیابی‌افزوده و اتصال به دانش بیرونی

پرسش‌های راهنما:

- RAG چه اجزای تازه‌ای به معماری اضافه می‌کند؟
- مرز مسئولیت بین retriever، vector store، reranker، prompt builder و مدل چیست؟
- خطاهای بازیابی چگونه به خطاهای خروجی تبدیل می‌شوند؟

### ۳. مدل، inference و serving

پرسش‌های راهنما:

- سرویس‌دهی مدل چه اثرهایی روی latency، throughput، هزینه و مقیاس‌پذیری دارد؟
- batching، caching، model routing یا استفاده از مدل‌های متفاوت چه موازنه‌هایی ایجاد می‌کند؟
- تغییر نسخه‌ی مدل چه اثر معماری دارد؟

### ۴. ارزیابی، آزمون‌پذیری و کیفیت خروجی

پرسش‌های راهنما:

- چرا تست سنتی برای این سرویس‌ها کافی نیست؟
- چه نوع ارزیابی‌هایی لازم است؟ offline، online، human evaluation، LLM-as-a-judge.
- چه معیارهایی برای دقت، پایداری، ایمنی و سودمندی خروجی قابل استفاده است؟

### ۵. امنیت، سوءاستفاده و کنترل دسترسی

پرسش‌های راهنما:

- prompt injection، data leakage و دسترسی غیرمجاز از کدام مسیرها وارد معماری می‌شوند؟
- کدام کنترل‌ها باید قبل و بعد از مدل قرار بگیرند؟
- مرز اعتماد بین کاربر، ابزار، مدل، داده و سرویس‌های داخلی کجاست؟

### ۶. مشاهده‌پذیری و عملیات

پرسش‌های راهنما:

- چه چیزهایی باید log، trace و monitor شوند؟
- مشاهده‌پذیری در سطح مدل، prompt، retrieval، latency، هزینه و کیفیت خروجی چگونه تعریف می‌شود؟
- چه alertهایی برای محیط تولید لازم است؟

### ۷. هزینه، کارایی و مقیاس‌پذیری

پرسش‌های راهنما:

- هزینه‌ی inference، embedding، retrieval و ارزیابی چگونه وارد طراحی معماری می‌شود؟
- چه تاکتیک‌هایی برای کنترل هزینه وجود دارد؟
- چه موازنه‌ای بین کیفیت، latency و هزینه شکل می‌گیرد؟

### ۸. نگهداشت‌پذیری، تکامل و بدهی فنی

پرسش‌های راهنما:

- وابستگی به مدل، prompt، داده و ابزارهای بیرونی چه نوع بدهی فنی ایجاد می‌کند؟
- تغییر مدل یا تغییر داده چگونه باید مدیریت شود؟
- چه قراردادها، نسخه‌بندی‌ها و تست‌هایی برای تکامل امن سیستم لازم است؟

## قالب ترکیب هر محور

برای هر محور در گزارش نهایی این ساختار را بنویسیم:

1. تعریف مسئله
2. چرایی معماری بودن مسئله
3. شواهد و دیدگاه منابع
4. ریسک‌ها و پیامدها
5. تاکتیک‌ها و راهکارهای پیشنهادی
6. شکاف‌ها و پرسش‌های باز
7. جمع‌بندی کوتاه
