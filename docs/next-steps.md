# مسیر ادامه‌ی کار

این سند برای این است که ادامه‌ی پروژه گم نشود. هر بار که کار را شروع می‌کنیم، اول این فایل را می‌خوانیم و بعد وضعیت را به‌روزرسانی می‌کنیم.

## وضعیت فعلی

- دامنه‌ی پروژه از «هوش مصنوعی مولد» به «چالش‌های معماری نرم‌افزار در سرویس‌های مبتنی بر GenAI/LLM/RAG» محدود شده است.
- رویکرد پروژه مروری و تحلیلی است، نه پیاده‌سازی ابزار.
- منابع اولیه در `references/references.bib` جمع‌آوری شده‌اند.
- چند اسکریپت برای اصلاح، بررسی و تکمیل رفرنس‌ها اضافه شده است.
- دو کتاب اصلی با اطلاعات کتاب‌شناختی دستی تکمیل شده‌اند.
- قالب مرور منابع و برنامه‌ی ترکیب منابع در پوشه‌ی `docs` اضافه شده است.

## اصل روش‌شناختی

کار را مثل یک مرور نظام‌مند سبک‌شده پیش می‌بریم:

1. پرسش‌های پژوهش روشن باشد.
2. معیار ورود و خروج منابع مشخص باشد.
3. خلاصه‌ی منابع قالب ثابت داشته باشد.
4. داده‌های معماری از منابع استخراج شود.
5. ترکیب نهایی بر اساس محورهای معماری باشد، نه بر اساس ترتیب مقاله‌ها.
6. تصمیم‌ها، حذف‌ها و تغییر مسیرها ثبت شوند.

## کارهای فردا

### ۱. آماده‌سازی پوشه‌ی خلاصه‌ها

پوشه‌ی زیر باید وجود داشته باشد:

```text
paper-summaries/
```

برای هر منبع مهم، یک فایل با نام کلید BibTeX ساخته شود. مثال:

```text
paper-summaries/barnett2024sevenFailurePointsRag.md
paper-summaries/stone2025navigatingMlops.md
paper-summaries/huyen2025aiEngineering.md
```

هر فایل باید از قالب `docs/paper-summary-template.md` ساخته شود.

### ۲. اولویت‌بندی منابع برای مطالعه

اول منابعی را بخوانیم که بیشترین ربط را به معماری تولیدی دارند:

1. `barnett2024sevenFailurePointsRag`
2. `stone2025navigatingMlops`
3. `huyen2025aiEngineering`
4. `engineeringAiSystems2025`
5. `xu2025ragops`
6. `kwon2023pagedattention`
7. `li2024llmInferenceServingSurvey`
8. `greshake2023indirectPromptInjection`
9. `owasp2025llmTop10`
10. `sculley2015hiddenDebt`

بعد از این‌ها سراغ منابع مروری عمومی‌تر برویم.

### ۳. خلاصه‌کردن هر منبع

برای هر منبع، فقط این سه خروجی را جدی بگیریم:

- این منبع چه مسئله‌ی معماری را روشن می‌کند؟
- چه چالش، ریسک یا تاکتیکی از آن قابل استخراج است؟
- در کدام بخش گزارش نهایی استفاده می‌شود؟

اگر منبعی فقط زمینه‌ی عمومی می‌دهد، خلاصه‌اش کوتاه باشد و وزن زیادی در گزارش نگیرد.

### ۴. ساخت جدول استخراج داده

بعد از خلاصه‌ی ۵ منبع اول، یک جدول مرکزی بسازیم:

```text
data/extracted-challenges.csv
```

ستون‌های پیشنهادی:

```text
source_key,challenge,architecture_layer,quality_attribute,risk,proposed_tactic,evidence_note,report_section,confidence
```

این جدول بعداً مبنای فصل تحلیل می‌شود.

### ۵. طراحی معماری نمونه‌ی RAG

بعد از چند خلاصه‌ی اول، یک معماری نمونه رسم شود. اجزای پیشنهادی:

- client
- api gateway
- application service
- prompt builder
- retriever
- vector database
- document store
- LLM provider / model serving
- cache
- queue
- evaluation service
- monitoring/logging/tracing
- access control layer

هدف از نمودار، نمایش چالش‌های معماری است، نه طراحی دقیق محصول.

### ۶. ساخت ستون فقرات گزارش نهایی

بعد از تکمیل خلاصه‌ها، گزارش نهایی با این خط روایی نوشته شود:

1. چکیده
2. مقدمه و صورت مسئله
3. روش مرور منابع
4. معماری نمونه‌ی سرویس مبتنی بر RAG
5. چالش‌های معماری در لایه‌های مختلف
6. اثر چالش‌ها بر ویژگی‌های کیفی
7. تاکتیک‌ها و راهکارهای پیشنهادی
8. جدول جمع‌بندی ریسک‌ها و تصمیم‌های معماری
9. شکاف‌ها و مسیرهای آینده
10. جمع‌بندی

## چک‌لیست شروع هر جلسه

قبل از شروع کار:

```bash
git pull
make fix-references
make check-references
```

بعد از تغییر رفرنس‌ها:

```bash
make fix-references
make check-references
make verify-references
```

بعد از اضافه‌کردن یا اصلاح کتاب‌ها:

```bash
python3 scripts/apply_manual_book_metadata.py
make fix-references
```

## چک‌لیست پایان هر جلسه

در پایان هر جلسه:

1. خلاصه‌ی کارهای انجام‌شده را در همین فایل اضافه کن.
2. اگر منبعی حذف یا کم‌اهمیت شد، دلیلش را بنویس.
3. اگر پرسش پژوهش تغییر کرد، در `docs/review-protocol.md` اصلاح کن.
4. تغییرات را commit کن.
5. کار بعدی را در بخش «کارهای جلسه‌ی بعد» بنویس.

## کارهای جلسه‌ی بعد

- ساخت پوشه‌ی `paper-summaries`.
- ساخت ۳ فایل خلاصه‌ی اول از روی قالب.
- شروع با `barnett2024sevenFailurePointsRag` چون مستقیماً درباره‌ی failure pointهای RAG است.
- بعد از آن `stone2025navigatingMlops` و `huyen2025aiEngineering` خوانده شوند.
- پس از سه خلاصه، اولین نسخه‌ی جدول چالش‌ها ساخته شود.

## نکته‌های احتیاطی

- گزارش نباید شبیه خلاصه‌ی کتاب و مقاله شود.
- هر بخش باید به معماری نرم‌افزار وصل شود.
- برای منابعی که فقط arXiv هستند، وزن تحلیلی کمتر در نظر بگیریم مگر اینکه بسیار مرتبط باشند.
- DOIهای مشکوک یا رفرنس‌های غیرقطعی نباید بدون بازبینی وارد متن نهایی شوند.
- هدف نهایی، یک گزارش تحلیلی و قابل دفاع است؛ نه جمع‌آوری تعداد زیادی منبع.
