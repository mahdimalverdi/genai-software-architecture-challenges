# گزارش نهایی: چالش‌های معماری در سامانه‌های GenAI

## وضعیت سند

این سند نسخه‌ی اولیه‌ی گزارش نهایی است. در این نسخه، سه بخش نخست گزارش نوشته شده‌اند: مقدمه و صورت مسئله، پیش‌زمینه و مفاهیم کلیدی، و RAG به‌عنوان مسئله‌ی معماری. مبنای این متن، خلاصه‌های موجود در پوشه‌ی `papers/`، طرح تفصیلی `docs/final-report-outline.md` و ماتریس `docs/architecture-challenges-matrix.md` است.

تمرکز این گزارش بر تحلیل معماری است، نه معرفی صرف مدل‌ها یا الگوریتم‌ها. بنابراین هرجا از مدل زبانی بزرگ، RAG، ارزیابی، امنیت یا serving صحبت می‌شود، هدف اصلی این است که نشان داده شود آن موضوع چه تصمیم معماری، چه ویژگی کیفی و چه ریسک طراحی ایجاد می‌کند.

## چکیده

سامانه‌های مبتنی بر GenAI، به‌ویژه سامانه‌هایی که از مدل‌های زبانی بزرگ، بازیابی‌افزوده و ابزارهای بیرونی استفاده می‌کنند، فقط یک مسئله‌ی مدل یا پیاده‌سازی نیستند. این سامانه‌ها به‌دلیل ماهیت احتمالاتی خروجی، وابستگی به داده و context بیرونی، حساسیت به prompt، دشواری ارزیابی، خطر prompt injection و هزینه‌ی عملیاتی inference، مجموعه‌ای از چالش‌های معماری ایجاد می‌کنند.

در یک سامانه‌ی کلاسیک، رفتار سیستم معمولاً با کد، داده‌ی ساخت‌یافته و قراردادهای نسبتاً صریح تعریف می‌شود. اما در سامانه‌ی GenAI، بخشی از منطق رفتاری در prompt، context، وزن‌های مدل، داده‌های بازیابی‌شده، evaluatorها و حتی ابزارهای متصل به مدل پخش می‌شود. این پراکندگی باعث می‌شود کیفیت سیستم فقط تابع کیفیت مدل نباشد، بلکه به طراحی کل زنجیره وابسته باشد: از ingestion و indexing گرفته تا retrieval، prompt assembly، generation، evaluation، logging، monitoring، release و governance.

پیام اصلی گزارش این است که سامانه‌های GenAI باید به‌عنوان سامانه‌های نرم‌افزاری معماری‌شده طراحی شوند. یعنی باید برای ویژگی‌هایی مانند قابلیت اطمینان، امنیت، مشاهده‌پذیری، قابلیت ارزیابی، هزینه، مقیاس‌پذیری، نگه‌داری‌پذیری و پاسخ‌گویی سازمانی تصمیم‌های معماری صریح گرفته شود. بدون این نگاه، سامانه ممکن است در demo خوب عمل کند، اما در محیط واقعی، با داده‌ی متغیر، ورودی خصمانه، بار عملیاتی، تغییر مدل و نیاز به audit دچار شکست شود.

## ۱. مقدمه و صورت مسئله

### ۱.۱ مسئله از کجا شروع می‌شود؟

رشد مدل‌های زبانی بزرگ باعث شده است که بسیاری از سامانه‌های نرم‌افزاری بتوانند قابلیت‌هایی مانند پاسخ‌گویی طبیعی، خلاصه‌سازی، جست‌وجوی معنایی، تولید متن، تحلیل سند، تولید کد و تصمیم‌یار هوشمند را در خود جای دهند. در نگاه اول، ممکن است اضافه کردن GenAI به یک محصول شبیه فراخوانی یک API مدل به نظر برسد: ورودی به مدل داده می‌شود و خروجی دریافت می‌شود. اما تجربه‌ی عملی و منابع بررسی‌شده نشان می‌دهند که این تصویر بسیار ساده‌سازی‌شده است.

در یک محصول واقعی، مدل معمولاً به‌تنهایی کار نمی‌کند. قبل از فراخوانی مدل، داده جمع‌آوری، پاک‌سازی، chunk، embedding و index می‌شود. هنگام درخواست کاربر، query ممکن است بازنویسی شود، چند سند بازیابی شود، context ساخته شود، prompt نهایی شکل بگیرد، مدل پاسخ دهد، پاسخ ارزیابی یا فیلتر شود و سپس خروجی به کاربر یا یک سیستم دیگر تحویل داده شود. اگر سیستم ابزارمحور باشد، مدل ممکن است تصمیم بگیرد API یا action مشخصی را اجرا کند. در چنین شرایطی، خطا فقط از مدل نمی‌آید؛ خطا می‌تواند از داده، بازیابی، رتبه‌بندی، prompt، سیاست‌های امنیتی، ابزارها، evaluator یا pipeline عملیاتی ناشی شود.

به همین دلیل، پرسش اصلی این گزارش چنین است:

> در طراحی سامانه‌های نرم‌افزاری مبتنی بر GenAI، به‌ویژه سامانه‌های RAG و ابزارمحور، چه چالش‌های معماری تکرارشونده‌ای پدیدار می‌شود و چه تاکتیک‌هایی می‌تواند این چالش‌ها را کنترل کند؟

### ۱.۲ چرا این موضوع معماری نرم‌افزار است؟

مسئله‌ی اصلی این نیست که مدل چه معماری داخلی دارد یا attention چگونه کار می‌کند؛ هرچند دانستن این مفاهیم برای فهم محدودیت‌ها مفید است. مسئله‌ی اصلی در سطح معماری نرم‌افزار این است که چگونه باید یک سیستم قابل اتکا، قابل پایش، قابل نگه‌داری و امن بر پایه‌ی مدلی ساخت که خروجی آن قطعی نیست و رفتار آن با prompt، context و نسخه‌ی مدل تغییر می‌کند.

در سامانه‌های کلاسیک، بسیاری از ویژگی‌های کیفی با الگوها و تاکتیک‌های شناخته‌شده مدیریت می‌شوند؛ برای مثال، availability با replication و failover، performance با caching و scaling، امنیت با authorization و input validation، و maintainability با modularity و testing. در سامانه‌های GenAI، این تاکتیک‌ها هنوز مهم‌اند، اما کافی نیستند. چون اجزای جدیدی وارد معماری می‌شوند که رفتار آن‌ها کمتر قابل پیش‌بینی است: مدل زبانی، prompt، embedding model، vector store، retriever، evaluator، agent و tool invocation.

برای نمونه، اگر یک پاسخ اشتباه تولید شود، تیم باید بتواند بفهمد مشکل از کجاست: آیا query کاربر بد فهمیده شده؟ آیا اسناد اشتباه بازیابی شده‌اند؟ آیا context کافی نبوده؟ آیا prompt نهایی ابهام داشته؟ آیا مدل hallucination کرده؟ آیا evaluator خطا را تشخیص نداده؟ یا آیا corpus قدیمی شده است؟ پاسخ به این پرسش‌ها بدون طراحی مشاهده‌پذیری، logging و trace در سطح معماری ممکن نیست.

همین مسئله در امنیت هم دیده می‌شود. در سامانه‌های GenAI، ورودی کاربر یا محتوای بازیابی‌شده فقط داده نیست؛ ممکن است حاوی دستور باشد. این موضوع مرز سنتی میان data و instruction را مبهم می‌کند. بنابراین کنترل امنیتی فقط در سطح API gateway یا احراز هویت کافی نیست؛ باید در سطح prompt، context، retrieval source، tool permission و policy gate هم طراحی شود.

### ۱.۳ تفاوت demo با سیستم production

بسیاری از سامانه‌های GenAI در مرحله‌ی نمونه‌سازی سریع موفق به نظر می‌رسند. یک prompt خوب، چند سند نمونه و یک مدل قدرتمند می‌تواند خروجی قانع‌کننده تولید کند. اما فاصله‌ی demo تا production معمولاً در همین چالش‌های معماری آشکار می‌شود.

در محیط واقعی، corpus تغییر می‌کند، کاربران ورودی‌های متنوع و گاهی خصمانه می‌دهند، مدل‌ها نسخه عوض می‌کنند، latency و هزینه اهمیت پیدا می‌کند، تیم محصول نیاز به metric دارد، تیم امنیت نگران data leakage است، تیم عملیات به monitoring و rollback نیاز دارد، و مدیران محصول می‌خواهند بدانند چه کسی مالک کیفیت خروجی است. این‌ها مسئله‌هایی نیستند که صرفاً با انتخاب مدل قوی‌تر حل شوند.

از این زاویه، معماری سامانه‌های GenAI باید چند دغدغه را همزمان پاسخ دهد:

- کیفیت پاسخ و groundedness؛
- امنیت prompt، retrieval و tool invocation؛
- مشاهده‌پذیری خطا در زنجیره‌ی چندمرحله‌ای؛
- ارزیابی پیوسته و regression testing؛
- هزینه و latency در serving؛
- lifecycle management برای مدل، prompt، index و داده؛
- governance و مالکیت کیفیت.

این گزارش، این دغدغه‌ها را به‌عنوان چالش‌های معماری بررسی می‌کند و تلاش می‌کند از منابع مختلف، تاکتیک‌های قابل دفاع استخراج کند.

## ۲. پیش‌زمینه و مفاهیم کلیدی

### ۲.۱ مدل زبانی بزرگ در سامانه‌ی نرم‌افزاری

مدل زبانی بزرگ، در ساده‌ترین بیان، مؤلفه‌ای است که بر اساس ورودی متنی و context، خروجی متنی تولید می‌کند. اما در سطح سامانه، مدل فقط یک تابع ساده نیست. رفتار آن به prompt، ترتیب اطلاعات، محدودیت context window، نسخه‌ی مدل، temperature، سیاست‌های decoding و حتی قالب خروجی وابسته است. بنابراین در طراحی معماری، مدل باید به‌عنوان یک مؤلفه‌ی probabilistic و versioned دیده شود، نه یک کتابخانه‌ی deterministic.

این نگاه چند پیامد دارد. اول اینکه خروجی مدل باید قابل ارزیابی و پایش باشد. دوم اینکه تغییر مدل یا prompt باید مانند تغییر کد یا تغییر schema مدیریت شود. سوم اینکه باید برای شکست مدل، پاسخ ضعیف، hallucination یا latency بالا، سیاست fallback و degradation وجود داشته باشد. چهارم اینکه اگر مدل به ابزارها وصل می‌شود، نباید اختیار اجرای action بدون کنترل معماری داشته باشد.

منبع `vaswani2017attention` در این گزارش بیشتر از منظر مبنایی استفاده می‌شود؛ یعنی توضیح اینکه مدل‌های Transformer و attention چگونه زمینه‌ی ظهور LLMهای امروزی را فراهم کردند. اما تمرکز گزارش، تحلیل داخلی Transformer نیست، بلکه اثر معماری استفاده از چنین مدل‌هایی در سامانه‌های نرم‌افزاری است.

### ۲.۲ RAG چیست و چرا وارد معماری می‌شود؟

بازیابی‌افزوده یا Retrieval-Augmented Generation با این ایده شکل می‌گیرد که مدل به‌جای اتکا به دانش ثابت درون وزن‌های خود، هنگام پاسخ‌گویی از منابع بیرونی هم استفاده کند. در یک pipeline رایج RAG، اسناد ابتدا ingest و chunk می‌شوند، سپس embedding تولید می‌شود و در vector store قرار می‌گیرد. هنگام درخواست کاربر، query به فضای embedding برده می‌شود، اسناد مرتبط بازیابی می‌شوند، گاهی reranking انجام می‌شود، context به prompt اضافه می‌شود و مدل پاسخ نهایی را تولید می‌کند.

این معماری در ظاهر ساده است، اما از نظر معماری چند نکته‌ی مهم دارد. RAG یک مؤلفه نیست؛ یک زنجیره است. هر مرحله‌ی این زنجیره می‌تواند خطا ایجاد کند. اگر chunking بد باشد، اسناد ناقص وارد index می‌شوند. اگر embedding مناسب نباشد، retrieval ضعیف می‌شود. اگر top-k بد تنظیم شود، context ناکافی یا شلوغ می‌شود. اگر prompt assembly درست نباشد، مدل از context استفاده نمی‌کند. اگر evaluator وجود نداشته باشد، پاسخ غلط تشخیص داده نمی‌شود.

منابعی مانند `lewis2020rag`، `gao2023ragSurvey`، `gupta2024ragComprehensiveSurvey` و `zhao2024ragAigcSurvey` از این جهت در گزارش مهم‌اند که نشان می‌دهند RAG فقط یک تکنیک افزایش دانش نیست، بلکه یک الگوی معماری برای اتصال مدل به دانش بیرونی است. همین اتصال، هم فرصت ایجاد می‌کند و هم ریسک: فرصت برای به‌روزرسانی دانش و کاهش hallucination؛ ریسک برای خطای بازیابی، آلودگی منبع، prompt injection غیرمستقیم و دشواری observability.

### ۲.۳ ارزیابی در GenAI چرا متفاوت است؟

در نرم‌افزارهای کلاسیک، تست‌ها معمولاً انتظار خروجی مشخصی دارند. اما در سامانه‌های GenAI، خروجی ممکن است از نظر لفظی متفاوت ولی از نظر معنایی درست باشد. همچنین ممکن است خروجی روان و قانع‌کننده باشد، اما پشتوانه‌ی واقعی نداشته باشد. بنابراین ارزیابی باید فراتر از مقایسه‌ی رشته‌ای خروجی باشد.

در RAG، معیارهایی مانند relevance، faithfulness، context precision و context recall اهمیت پیدا می‌کنند. در سامانه‌های عمومی‌تر، معیارهایی مانند correctness، completeness، harmfulness، groundedness و consistency مطرح می‌شوند. منابعی مانند `es2023ragas`، `liu2023geval`، `zheng2023llmJudge`، `yu2024ragEvaluationSurvey` و `saadfalcon2023ares` نشان می‌دهند که evaluation pipeline خود باید به‌عنوان بخشی از معماری طراحی شود.

این موضوع در گزارش بعداً به یک اصل معماری تبدیل می‌شود: evaluation نباید فعالیتی دستی و پسینی باشد؛ باید در چرخه‌ی توسعه و عملیات سیستم قرار بگیرد. به بیان دیگر، همان‌طور که CI/CD برای کد اهمیت دارد، quality gates و regression evaluation برای مدل، prompt، index و corpus هم اهمیت دارند.

### ۲.۴ serving و هزینه‌ی عملیاتی

مدل‌های زبانی بزرگ از نظر اجرا پرهزینه‌اند. latency، throughput، مصرف حافظه، batching، KV cache، prefill و decode همگی بر تجربه‌ی کاربر و هزینه‌ی سیستم اثر دارند. منابعی مانند `kwon2023pagedattention`، `zheng2023sglang`، `zhong2024distserve` و `li2024llmInferenceServingSurvey` نشان می‌دهند که serving LLMها یک مسئله‌ی جدی معماری و زیرساختی است.

از دید معماری نرم‌افزار، پرسش فقط این نیست که کدام مدل دقیق‌تر است. باید پرسید آیا برای همه‌ی درخواست‌ها باید مدل بزرگ استفاده شود؟ آیا می‌توان model routing داشت؟ آیا caching پاسخ یا context ممکن است؟ آیا سیستم fallback دارد؟ آیا برای latency بالا سیاست timeout و degradation تعریف شده؟ آیا ظرفیت GPU و memory با الگوی ترافیک سازگار است؟ این پرسش‌ها نشان می‌دهند که GenAI در production بدون طراحی serving و capacity planning، ناپایدار و گران می‌شود.

### ۲.۵ LLMOps، RAGOps و governance

در سامانه‌های GenAI، چرخه‌ی عمر فقط شامل کد نیست. مدل، prompt، داده، embedding model، index، evaluator و policyها هم نسخه دارند و تغییر می‌کنند. بنابراین عملیات چنین سامانه‌هایی به رویکردی شبیه MLOps ولی گسترش‌یافته نیاز دارد. منابعی مانند `stone2025navigatingMlops`، `huyen2025aiEngineering`، `engineeringAiSystems2025` و `xu2025ragops` این موضوع را از زاویه‌ی lifecycle، monitoring و governance برجسته می‌کنند.

اگر تیم نداند کدام نسخه‌ی prompt با کدام نسخه‌ی index و کدام نسخه‌ی مدل در production بوده، عیب‌یابی و rollback دشوار می‌شود. اگر quality owner مشخص نباشد، کیفیت خروجی بین تیم‌های محصول، داده، backend، مدل و عملیات پخش می‌شود. اگر logها شامل داده‌ی حساس باشند، مسئله‌ی privacy ایجاد می‌شود. اگر risk register و policy وجود نداشته باشد، سیستم ممکن است در برابر ریسک‌های امنیتی و اخلاقی آسیب‌پذیر شود.

به همین دلیل، governance در این گزارش یک بحث حاشیه‌ای نیست؛ بخشی از معماری عملیاتی سامانه است.

## ۳. RAG به‌عنوان مسئله‌ی معماری

### ۳.۱ RAG فقط اضافه کردن retriever نیست

یکی از خطاهای رایج در طراحی سامانه‌های GenAI این است که RAG به‌عنوان یک افزونه‌ی ساده دیده شود: چند سند را در vector database می‌ریزیم، نزدیک‌ترین‌ها را بازیابی می‌کنیم و به مدل می‌دهیم. این نگاه برای demo کافی است، اما برای سیستم production خطرناک است.

RAG از چندین مرحله تشکیل شده است و هر مرحله قرارداد، کیفیت و شکست خاص خود را دارد. ingestion باید بداند چه داده‌ای وارد سیستم می‌شود. chunking باید مرزهای معنایی متن را حفظ کند. embedding باید با نوع queryها و زبان داده‌ها سازگار باشد. retriever باید اسناد مرتبط را پیدا کند. reranker باید اولویت را اصلاح کند. prompt assembly باید context را به‌شکلی وارد کند که مدل واقعاً از آن استفاده کند. generator باید پاسخ را بر اساس context بسازد. evaluator باید کیفیت و faithfulness را بسنجد. logging باید امکان trace را فراهم کند.

بنابراین RAG یک pipeline معماری است، نه یک تکنیک منفرد. این pipeline باید قابل مشاهده، قابل ارزیابی، قابل نسخه‌بندی و قابل عیب‌یابی باشد.

### ۳.۲ خطای مرحله‌ای و دشواری تشخیص منشأ خطا

چالش `C01` در ماتریس معماری، خطای مرحله‌ای در زنجیره‌ی RAG است. این چالش می‌گوید پاسخ نهایی ممکن است غلط باشد، اما منشأ خطا آشکار نباشد. اگر سیستم فقط ورودی کاربر و خروجی مدل را ذخیره کند، تیم نمی‌تواند بفهمد چه اتفاقی افتاده است. برای عیب‌یابی باید بداند query چگونه پردازش شده، چه اسنادی بازیابی شده، چه contextی وارد prompt شده، مدل با چه تنظیماتی فراخوانی شده و evaluator چه نتیجه‌ای داده است.

به‌عنوان مثال، فرض کنیم کاربر درباره‌ی سیاست جدید یک سازمان سؤال می‌پرسد و سیستم پاسخ قدیمی می‌دهد. این خطا ممکن است از چند جا آمده باشد: corpus به‌روز نشده، index قدیمی است، retriever سند جدید را پیدا نکرده، سند درست بازیابی شده ولی در رتبه‌ی پایین بوده، context بیش از حد طولانی بوده و بخش مهم حذف شده، یا مدل با وجود context درست، hallucination کرده است. هرکدام از این منشأها تاکتیک متفاوتی می‌خواهد. بدون observability، همه‌ی این‌ها به‌صورت یک خطای مبهم دیده می‌شوند: «مدل جواب بد داد».

این دقیقاً نقطه‌ای است که RAG را به مسئله‌ی معماری تبدیل می‌کند. معماری باید امکان تفکیک خطا را فراهم کند.

### ۳.۳ کیفیت context و اثر آن بر پاسخ نهایی

چالش `C02` به کیفیت پایین یا ناکافی بودن context مربوط است. در RAG، مدل هرچقدر هم قوی باشد، اگر context نامربوط، ناقص یا آلوده باشد، احتمال تولید پاسخ غلط بالا می‌رود. بنابراین کیفیت retrieval و کیفیت generation باید جداگانه سنجیده شوند.

برای کنترل این مسئله، گزارش بر چند تاکتیک تأکید می‌کند. نخست، باید معیارهای retrieval مانند hit@k، context precision و context recall تعریف شود. دوم، باید golden set برای queryهای مهم نگه‌داری شود تا تغییر index یا embedding model قابل ارزیابی باشد. سوم، باید reranking و query rewriting در مواردی که retrieval ضعیف است بررسی شود. چهارم، باید نسخه‌ی corpus، embedding model و index ثبت شود تا افت کیفیت قابل ردیابی باشد.

منابع ارزیابی RAG مانند `es2023ragas` و `yu2024ragEvaluationSurvey` از این جهت مهم‌اند که نشان می‌دهند ارزیابی RAG باید چندبخشی باشد. یک پاسخ ممکن است از نظر زبانی خوب باشد اما به context وفادار نباشد. یا ممکن است پاسخ درست باشد، اما context بازیابی‌شده تصادفاً ناکافی بوده و سیستم در queryهای مشابه شکست بخورد. بنابراین ارزیابی فقط روی پاسخ نهایی کافی نیست.

### ۳.۴ منابع بیرونی و مرز اعتماد

RAG با منابع بیرونی کار می‌کند. این ویژگی مزیت اصلی آن است، اما همزمان یک ریسک امنیتی و کیفی ایجاد می‌کند. وقتی سیستم از اسناد، صفحات وب، ticketها، wiki، ایمیل، یا محتوای تولیدشده توسط کاربر context می‌سازد، باید سطح اعتماد هر منبع مشخص باشد. همه‌ی اسناد ارزش و ریسک یکسان ندارند.

چالش `C06` در ماتریس به همین موضوع اشاره می‌کند: ریسک استفاده از منابع بیرونی در RAG و agentها. اگر منبع بیرونی خصمانه یا آلوده باشد، می‌تواند دستور پنهان وارد context کند. این حالت به prompt injection غیرمستقیم مربوط می‌شود. حتی اگر منبع خصمانه نباشد، ممکن است قدیمی، ناقص یا نامعتبر باشد. بنابراین معماری RAG باید provenance، سطح اعتماد source، policy دسترسی و ثبت مسیر داده را در نظر بگیرد.

یک تاکتیک عملی این است که sourceها طبقه‌بندی شوند: منابع رسمی، منابع داخلی قابل اعتماد، منابع کاربر، منابع وب عمومی و منابع ناشناس. سپس سیستم بر اساس این طبقه‌بندی تصمیم بگیرد کدام داده وارد context شود، کدام داده نیاز به فیلتر دارد، کدام داده نباید ابزار را تحریک کند و کدام پاسخ باید همراه با citation یا هشدار باشد.

### ۳.۵ مشاهده‌پذیری در RAG

چالش `C11` به نبود observability کافی برای عیب‌یابی پاسخ مربوط است. در RAG، log سنتی request/response کافی نیست. سیستم باید trace انتهابه‌انتها داشته باشد. این trace باید حداقل شامل موارد زیر باشد:

- شناسه‌ی درخواست و کاربر یا session در سطح مجاز؛
- query اولیه و نسخه‌ی بازنویسی‌شده‌ی آن؛
- اسناد بازیابی‌شده و رتبه‌ی آن‌ها؛
- نسخه‌ی corpus، index و embedding model؛
- prompt assembled نهایی، با رعایت سیاست‌های privacy؛
- نسخه‌ی مدل و پارامترهای generation؛
- خروجی مدل؛
- نتیجه‌ی evaluatorها و معیارهای کیفیت.

بدون این داده‌ها، تیم نمی‌تواند regressionها را تشخیص دهد یا تصمیم بگیرد مشکل با tuning retriever حل می‌شود، با اصلاح prompt، با به‌روزرسانی corpus یا با تغییر evaluator. بنابراین observability در RAG یک قابلیت عملیاتی جانبی نیست، بلکه تاکتیک مرکزی معماری است.

### ۳.۶ جمع‌بندی بخش RAG

RAG باید به‌عنوان یک زنجیره‌ی معماری دیده شود که چند ویژگی کیفی را همزمان درگیر می‌کند: correctness، reliability، security، traceability، testability و maintainability. اگر این زنجیره به‌صورت یک black box طراحی شود، کیفیت سیستم قابل کنترل نخواهد بود. اما اگر مراحل آن تفکیک، نسخه‌بندی، ارزیابی و trace شوند، می‌توان RAG را از یک prototype جذاب به یک قابلیت قابل اتکا در production تبدیل کرد.

جمع‌بندی این بخش چنین است: شکست RAG معمولاً شکست یک مرحله نیست؛ شکست هماهنگی میان داده، retrieval، prompt، مدل، evaluation و عملیات است. بنابراین راه‌حل آن هم صرفاً انتخاب مدل بهتر نیست، بلکه طراحی معماری بهتر است.
